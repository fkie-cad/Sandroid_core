# Sandroid Framework

Sandroid provides a powerful **Android sandbox framework** that enables automated analysis of Android applications.
It combines both **static** and **dynamic** techniques to help security researchers, forensic analysts, and malware analysts better understand how apps behave in a controlled environment.

By using this framework, you can:

- **Extract forensic artifacts** generated by Android apps and identify which app created them.
- **Analyze malware behavior** through automated static and dynamic analysis.
- **Uncover security vulnerabilities** and misconfigurations in Android applications.
- Gain deeper insights into app behavior without manual reverse engineering.

The framework is designed to simplify the process of **forensic investigations**, **mobile threat detection**, and **security testing** by providing a streamlined, automated environment for analysis.
Whether you're investigating malicious apps, assessing security flaws, or collecting digital evidence, this solution helps you quickly identify and understand what happens inside Android applications.

## Requirements

- **Python 3.12 or 3.13** (Python 3.10/3.11 are no longer supported as of 2.1).
- **Android SDK** platform-tools (`adb`) and the Android Emulator (e.g. via Android Studio). `sandroid-config init` auto-detects both.
- **A rooted Android emulator (AVD).** Sandroid needs root on the device (it runs `adb root`, pushes and starts `frida-server`, and sets SELinux to *permissive* with `setenforce 0` itself). Two setups are known to work:
  - a **Google APIs** system image (`google_apis`, *not* `google_apis_playstore`) — `adb root` works out of the box; or
  - a **Google Play** system image rooted with [rootAVD](https://gitlab.com/newbit/rootAVD) (Magisk) **plus the Magisk `adb_root` module**, so that `adbd` itself runs as root. This is how the Sandroid team's own AVDs are set up.
- **AVD snapshots** must be enabled — the record/play workflow and the snapshot picker (`S`) rely on them. Do **not** start the emulator with `-no-snapshot`; if you do not want the emulator to overwrite its quick-boot snapshot on exit use `-no-snapshot-save` (or simply start it via `sandroid-config avd start`).
- **Physical devices** are only partially supported: they must be rooted, and everything that relies on the emulator (snapshots, emulator-console network capture/degradation, `-no-snapshot-*` boot modes) is unavailable.
- Linux and macOS are the primary platforms; Windows works best via WSL2.

## Quick Start

```bash
# Install from PyPI
pip install sandroid

# Initialize configuration (detects the Android SDK and lets you pick/create an AVD)
sandroid-config init

# Start your AVD (keeps snapshots enabled)
sandroid-config avd start

# Launch the interactive TUI
sandroid
```

See [SETUP.md](SETUP.md) for all installation possibilities.

## Interactive TUI

Sandroid's default interface is an interactive terminal UI (Textual) built around **lenses**: one full-width analysis view at a time, details only on demand. Top to bottom: a one-row **header** (device ▸ app breadcrumb, the `● LIVE` / `◆ REVIEW` scope pill, clock), a 1–2 row **status strip** (app state, frida-server, hooks/bypass, proxy), the **lens bar**, the active lens, a one-row **log ticker** (newest log line) and the footer.

| Key | Lens | What it shows |
|---|---|---|
| `1` | **App** | The app under investigation: start / resume (`Enter`), attach (`A`), start paused (`P`), restart (`R`), kill (`K`), clear (`X`); `b` then `1`–`5` toggles the Frida bypass categories (SSL, Root, Frida, Debug, Integrity), `b` `o` opens Objection. |
| `2` | **Network** | Who the app talks to and what it sent: one flow table (time · recipient · request · status · size) from the embedded `mitmweb`, `Enter` for Summary / Request / Response in the Inspector; TLS failures show as ✗ rows. `/` filters (host, path, app or status; `Esc` clears it), `T` shows the spotlight (target) app only, `N` shows OS noise (hidden by default; the caption says how many flows it hides). `Home`/`End` jump to the first/last flow. Proxy state sits in the frame caption; `I` opens the Capture status page (mitmproxy + friTap). See below. |
| `3` | **Files** | One table of live file activity per file; watched files (★, `w`) are pinned on top and pulled/diffed with `u`/`U`. `N` shows the hidden noise (caches, temp files, OS paths), as in the Network lens. |
| `4` | **Runs** | Record → Play run history with the changed / new / deleted diffs (see below). |

`Shift+←/→` also cycles the lenses. `Enter` on a row opens the **Inspector** on the right where a lens supports it; `Esc` closes it. `Ctrl+Y` opens the **AI Chat** in the same right-hand slot. `` ` `` (backtick) opens the **log drawer** with the full activity log.

**Snapshots** are a picker, not a tab: `S` (or `0`) lists the AVD's snapshots — create (`c`), load (`Enter`/`l`, confirmed), delete (`d`), assign to a slot (`a`), load slot `1`–`8` (confirmed), and `s` then a digit saves the current state into a slot (8 slots per AVD). `Ctrl+1`–`Ctrl+8` save into a slot directly, but `Ctrl`+digit only reaches Sandroid in terminals with the kitty keyboard protocol (kitty, WezTerm, foot, Ghostty, recent iTerm2).

`?` opens the **help & keybinding editor** (every action grouped by category; rebind any key with live conflict detection, persisted to `tui.keybindings`), `Ctrl+Shift+P` opens the **command palette**, `D` switches devices and `q` (or `Ctrl+C` / `Ctrl+Q`) quits after a confirmation; quitting stops mitmweb and friTap and clears the device proxy Sandroid set, and never hangs on a tool that does not stop. Common operations are a single keypress (e.g. `y` proxy settings, `w` network capture, `o` file monitor, `f` frida-server, `s` screenshot, `n` install APK, `Ctrl+P` toggle SSL unpinning).

> The 2.0 "views" (Forensic / Malware / Security, switched with `TAB`) are gone — all actions live in one flat catalog. Fully non-interactive runs are available via `--headless`.

### Record → Play and run history

From any panel, `r` records your interactions with the device (Esc/Enter in the recording window stops and saves) and `p` plays them back, landing on the **Runs** lens (`4`): Sandroid reverts the emulator to the snapshot taken before recording, replays the recording, measures background noise with a dry run of the same duration (unless `--avoid-strong-noise-filter`) and diffs the filesystem, so only artifacts caused by your action remain (changed / new / deleted files with inline diffs, processes, sockets, network). Every Play is stored as a self-contained **run bundle** under `<results_path>/runs/<run_id>/` (`run.json` manifest, `recording.txt`, the raw pull tree) and listed in the Runs lens, scoped to the active device. Runs are never deleted automatically. `Enter` on a run opens its summary, changes and report in the Inspector; `v` **reviews** it — the header shows `◆ REVIEW #<n> <run>` and the Files and Network lenses show that run instead of the live session until `L` (or `v` again) returns to LIVE. `p` asks before it reverts the device (with the recording's name and an estimated duration); while it runs the header shows the phase (`● REPLAY · replay 1/2`, `dry run`, `analysing`). A run's mitmproxy flows are stored in its bundle (`network/flows.jsonl`, covered by `SHA256SUMS`) tagged by phase, so REVIEW shows the replays' traffic — also in a later session — with the dry-run noise hidden (`A` shows it). Runs of the same recording that disagree strongly are flagged `≠` in the Runs table, the Inspector and `=` compare.

### File monitor (kprobe)

The file monitor (`o`) streams filesystem events from the device into the **Files** lens. The default backend (`tui.monitor_backend = "kprobe"`) uses kernel tracefs kprobes: kernel-verified per-PID attribution, following the whole child-process tree, path-scoped capture, and no binary pushed to the device. On kernels without the required support it falls back to the `fsmon` binary automatically (or set `monitor_backend = "fsmon"`).

An app's data directory is watched under all its names (`/data/data/<pkg>`, `/data/user/0/<pkg>`, `/data/user_de/0/<pkg>`) and shown as one row per file. Each write is named by the kernel at write time (the write probe reads the file's directory chain), so writes through files the app opened before the monitor started -- its databases, when you attach to a running app -- appear live like any other. Watched files and every pulled version with its diff (newest `tui.watchlist_max_versions`, default 10) are kept per device under `~/.config/sandroid/watchlists/` and survive a restart.

## Network Interception & Bypass

Sandroid can route a target app's traffic through an embedded **mitmproxy** instance and defeat the common defences that get in the way of inspection. Everything lives in the **Network** lens (`2`); each step is its own keystroke, so none has a surprising side effect on the others:

| Key | Action |
|---|---|
| `Enter` (while nothing is captured) / `M` | start / stop `mitmweb` (proxy on `mitmproxy.proxy_port`, web UI on `mitmproxy.web_port`; defaults `127.0.0.1:8080` and `http://127.0.0.1:8081/`); start does **not** touch the device unless `mitmproxy.auto_device_proxy = true` |
| `Ctrl+D` | toggle the **Device Proxy** (global `http_proxy` setting → our mitmproxy) |
| `Ctrl+N` | install the mitmproxy CA into the device's **system** trust store |
| `y` | **Proxy Settings** modal: Device Proxy, **App Proxies** and CA in one place |
| `Ctrl+R` | restart `mitmweb` and re-apply device + app proxies |
| `Ctrl+O` / `Ctrl+A` | open the web UI (already logged in with its access token) / manage addons |
| `I` | Capture status page (mitmproxy and friTap state, keys, recent messages); mitmproxy's messages also go to the log drawer (`` ` ``) |

Requires `mitmweb` on `PATH` (`pip install mitmproxy`).

Ports come from `[mitmproxy]` in the config (`proxy_port`, `web_port`). mitmproxy listens on `127.0.0.1` only (`mitmproxy.listen_host`), so intercepted traffic is not exposed to the LAN. That is enough for emulators (the device reaches the host loopback as `10.0.2.2`) and for USB devices routed via `adb reverse` (Proxy Settings, `y`). Only a physical device on Wi-Fi needs `listen_host = "0.0.0.0"`. Starting mitmproxy leaves the device alone by default; set `mitmproxy.auto_device_proxy = true` to also point the Device Proxy at it on `Enter`. The Device Proxy Sandroid set is cleared when mitmproxy stops and when Sandroid exits.

**App Proxies.** Besides the global device proxy, individual apps can be routed through a proxy *per UID*: Sandroid pushes a small [gost](https://github.com/go-gost/gost) redirector to the device and adds iptables `REDIRECT` rules for that app only — either to Sandroid's mitmproxy or to an external proxy such as Burp or ZAP. QUIC (UDP/443) is blocked for proxied apps by default (`focus.block_quic`) so they fall back to interceptable TCP/TLS. On emulators the host IP is detected automatically; an `adb reverse` fallback is offered when the device cannot reach the host.

**CA certificate injection.** Sandroid auto-detects the host CA certificate from mitmproxy (`~/.mitmproxy/mitmproxy-ca-cert.pem`), HTTP Toolkit, or Burp Suite (a custom path is also accepted) and injects it into the device's system trust store. On Android 14+ (API ≥ 34) it bind-mounts the certificate into the Conscrypt APEX trust store; on Android 10–13 it injects into the Zygote mount namespace (after confirmation, since this restarts Zygote). It also writes the Chrome command-line flags needed to bypass Certificate Transparency enforcement.

**Certificate-pinning & detection bypass — EXPERIMENTAL.** Sandroid ships a Frida-based bypass suite with five categories — **SSL** unpinning, **Root**, **Frida**, **Debug** and **Integrity** (PairIP / licensing / attestation gates) detection — toggled with `1`–`5` in the **Spotlight** tab (`Ctrl+P` is a global shortcut for SSL unpinning). SSL unpinning is tiered: Java (`SSLContext`, OkHttp `CertificatePinner`, Conscrypt, WebView, TrustKit, Certificate Transparency), native BoringSSL, Chromium/cronet BoringSSL (including stripped, symbol-less builds), and mbedTLS / Meta Network Stack, with early-init hooks and a spawn-reliability ladder for hardened apps. All categories live in a single resident, flag-gated Frida script, so toggling one is instant and never leaves the app momentarily un-hooked. These bypasses are under active development: expect individual apps to defeat them, and verify results independently.

> These bypasses require a rooted AVD with `frida-server` running and a target app attached or spawned first.

**Custom mitmproxy addons.** You can load your own [mitmproxy addons](https://docs.mitmproxy.org/stable/addons-overview/) alongside Sandroid's built-in traffic logger. An addon is a standard mitmproxy script — a Python file that defines event hooks like `def response(flow): ...`, optionally a class exposing `addons = [...]`. Sandroid scans two drop-in folders for top-level `*.py` files (an `examples/` subdirectory is ignored):

- `~/.config/sandroid/mitm_addons/` — per-user; created on first run with a `README.md` and an `examples/example_logger.py` template.
- `./mitm_addons/` in the current working directory — handy for shipping addons together with a project.

To enable addons, press `Ctrl+A` in the Network lens for the addon manager — a checklist of every discovered addon. Tick the ones to load (or type a custom path directly); the selection is saved to your config under `mitmproxy.enabled_addons` and restored on the next run. A minimal addon looks like this:

```python
# ~/.config/sandroid/mitm_addons/log_urls.py
def response(flow):
    print(f"[my-addon] {flow.request.pretty_url} -> {flow.response.status_code}")
```

Editing an already-loaded addon file **hot-reloads** it live — no restart, no dropped traffic. Changing *which* addons are enabled restarts `mitmweb` (which briefly resets the live flow counters).

> Addons run as arbitrary, unsandboxed Python with the proxy process's privileges. Only enable scripts you trust.

With its modular architecture, Sandroid integrates multiple companion tools to cover a wide range of analysis capabilities — from cryptographic key extraction to TLS interception and network traffic decryption.

## AI Chat (EXPERIMENTAL)

Sandroid includes an LLM-backed chat assistant that can drive the same device and analysis actions as the TUI, talking to any **OpenAI-compatible** chat-completions endpoint you configure. The feature is **experimental**: tool behaviour, prompts and configuration may change between minor releases.

> **Data egress.** Everything the assistant sees — your prompts, the live device/session context Sandroid attaches to every turn, and the output of the tools it calls (file listings, file contents, captured flows, package data, …) — is sent to the configured endpoint. When analysing sensitive evidence or customer data, **use a local endpoint** (e.g. [Ollama](https://ollama.com), LM Studio, llama.cpp server or vLLM) instead of a cloud provider.

**Configuration.** Chat is inert until you set three connection fields — `base_url`, `api_key`, and `model`. Set the API key via an **environment variable** rather than the config file:

```bash
# recommended: secrets via environment variables
export SANDROID_AI__API_KEY="sk-..."
```

```toml
# ~/.config/sandroid/sandroid.toml -- example for a local Ollama instance
[ai]
base_url = "http://localhost:11434/v1"
model = "qwen2.5:14b"      # any tool-calling capable model you have pulled
# api_key: Ollama ignores it, but Sandroid requires a non-empty value -> export SANDROID_AI__API_KEY=ollama
```

`SANDROID_AI__BASE_URL` and `SANDROID_AI__MODEL` work as environment variables as well. A key written into the config file is stored in plaintext (`sandroid-config show` only redacts it for display).

**Opening it.** Press `Ctrl+Y` to open the Chat dock (a non-modal panel; the binding is rebindable like every other action — see `?`).

**What it can do.** Around 76 native tools spanning app/process lifecycle control, device/network/flow queries, certificate and environment control, host↔device file transfer, file monitoring and record/replay — plus two subagent tools that spawn read-only or (with approval) fully privileged background investigations, and anything exposed by MCP servers you configure under `[mcp]`. Host file access is confined to `ai.data_share_path` (default `~/Sandroid/ai_share/`), the current session's results directories and any `ai.extra_host_paths`.

**Safety.** Every tool call passes a permission gate — read-only calls run automatically, state-changing calls prompt for approval (allow once / always / never, persisted) — and a resource arbiter keeps the assistant and any concurrent subtasks from colliding on shared device resources such as the proxy, mitmproxy, frida-server, and snapshots. Still: review what you approve; the model can be wrong or manipulated by content it reads (e.g. strings inside an analysed app).

> The bundled `sandroid-dummy` MCP server is a demo only: everything it returns (e.g. its sample threat-intel lookup) is fabricated data, not a real result.


# Ground Truth APK
The framework also includes a custom Android app for testing and calibration.
This app is designed to **create specific forensic artefacts with pinpoint accuracy** at the user's command, while being as minimal as possible to avoid unintended artefacts.
To use it, simply install it on the emulator using Sandroid's built-in APK installer and open the app.

## Supported Artefacts
The app shows ten buttons; nine of them create an artefact (button label in quotes):
- "Create a new file" – `files/file_<n>.txt`
- "Add Database Entry" – row in `GroundTruth.db`
- "Delete Database Entry" – row removed from `GroundTruth.db`
- "Update Database Entry" – row updated in `GroundTruth.db`
- "Send 42 Bytes to 'fkie.fraunhofer.de'" – 42 bytes over TCP to `fkie.fraunhofer.de:443`
- "Start process 'yes'" – a running `yes` process
- "Add XML Entry" – entry in `GroundTruth.xml`
- "Delete XML Entry" – entry removed from `GroundTruth.xml`
- "Update XML Entry" – entry updated in `GroundTruth.xml`

The tenth button, "Download APK", is a placeholder and currently does nothing (no artefact).
Simply press the corresponding button to generate the artefact.

## Some considerations
- Values added to the XML file and the Database will be the current unix time on the emulator. It can deviate from the actual time but will be automatically be highlighted in the output.
- The first time the application is launched after installation, the XML file and database will be initialised, and Android will create a profile for the application, so **it is recommended that you open the application first, and only then start any analysis.**
- The XML and database files are called `GroundTruth.xml` and `GroundTruth.db` respectively and are stored in the applications directory. `GroundTruth.db` is only created by the first database button, and SQLite keeps fresh writes in `GroundTruth.db-wal` (with `-shm`) until a checkpoint, so expect those files in the diff as well.

## Configuration Management

The installation includes a configuration system (TOML by default):

```bash
# Initialize configuration
sandroid-config init

# View configuration
sandroid-config show

# Modify settings
sandroid-config set -k analysis.capture_network -v true
sandroid-config set -k emulator.device_name -v "Pixel_8_Pro_API_34"

# Validate configuration
sandroid-config validate
```

Configuration files (`sandroid.toml`, also `.yaml`/`.yml`/`.json`) are discovered in this order — `sandroid-config paths` prints the exact list for your system:
- `./sandroid.toml` (current directory, highest priority)
- `~/.config/sandroid/sandroid.toml` (user config)
- the platform config directory (e.g. `~/Library/Application Support/sandroid/` on macOS)
- Environment variables with the `SANDROID_` prefix override file values; nested keys use a double underscore, e.g. `SANDROID_AI__MODEL`.

## Contributing

We welcome contributions to Sandroid! Before contributing:

1. **Review Coding Guidelines**: Please read our comprehensive [CODING_GUIDELINES.md](CODING_GUIDELINES.md) which covers:
   - Python code style standards (PEP 8 compliance)
   - Architecture patterns specific to Sandroid
   - Testing requirements and best practices
   - Security considerations for forensic tools
   - Documentation standards
   - The release process

2. **Development Setup**:
   ```bash
   git clone git@github.com:fkie-cad/Sandroid_core.git
   cd Sandroid_core
   git checkout dev
   pip install -e ".[dev,full]"
   pytest            # ~1100 tests; never touch a real device (see tests/conftest.py)
   ```

3. **Submit Changes**: Fork the repository, create a feature branch off `dev`, ensure tests and `ruff check .` pass, and submit a pull request against `dev`.
